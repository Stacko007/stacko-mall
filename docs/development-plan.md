# 商城业务开发计划

本文档记录 `stacko-mall` 围绕用户中心和 Gateway 底座后的业务完善计划。执行方式采用分阶段推进：每完成一个阶段，先完成代码、数据库脚本、前后端联调点和验证记录，再进入下一阶段。

## 1. 当前基线

### 1.1 接入边界

- 客户端统一访问 Gateway。
- `/user/**` 透传到用户中心，由用户中心负责登录、注册、刷新、租户、门户和权限。
- `/mall/**` 由 Gateway 解析用户中心会话并签发 `X-Stacko-Identity` V4。
- 商城只验证 Gateway V4 身份，不集成 Sa-Token，不读取认证 Redis，不逐请求查询用户中心。
- 商城管理端固定使用 `stacko-mall-admin` 门户和 audience。
- 商城用户端固定使用 `stacko-mall-web` 门户和 audience。

### 1.2 已实现能力

- 商品基础维护：名称、描述、价格、状态。
- 商品库存：按商品维度设置、调整和查询。
- C 端基础链路：商品列表、商品详情、购物车、本地下单、模拟支付、订单列表、订单详情。
- 管理端基础链路：商品、库存、订单、支付、售后管理。
- 订单流程：创建、支付、取消、后台关闭、后台发货。
- 支付与售后：Mock 支付、支付回调幂等、售后申请、审核和退款。
- 安全：管理端接口使用 `@RequiresPermission`，商城验证 Gateway V4 身份和门户边界。

### 1.3 主要缺口

- 缺少商品多层级类目管理。
- 商品没有与类目建立业务关联。
- 缺少 C 端确认收货接口和页面操作，订单闭环未完成。
- 商品维护缺少图片上传，C 端商品列表和详情缺少图片展示。
- 商品缺少规格和 SKU，库存仍是商品级库存。
- C 端缺少收货地址管理，下单没有地址快照。
- C 端缺少登录后的商品收藏。
- 登录页要求用户手动输入租户 ID，用户体验不友好。

## 2. 执行顺序

### 阶段 1：补齐确认收货闭环

目标：完成“加入购物车 -> 下单 -> 模拟支付 -> 后台发货 -> 用户确认收货 -> 订单完成”主流程。

后端改造：

- 新增 C 端接口 `POST /api/c/orders/{id}/confirm`。
- 新增 `ConfirmReceiptCommand` 或等价命令对象。
- `OrderApplicationService` 增加确认收货用例。
- 复用领域模型已有 `SHIPPED -> COMPLETED` 状态规则。
- 校验订单必须属于当前登录买家。
- 建议使用 `X-Idempotency-Key`，幂等业务类型为 `ORDER_CONFIRM`。

前端改造：

- C 端订单列表和订单详情在 `SHIPPED` 状态展示“确认收货”操作。
- 确认成功后刷新订单状态，展示完成时间。

验证点：

- 非买家不能确认他人订单。
- 非 `SHIPPED` 状态不能确认。
- 重复确认不会产生错误状态或重复副作用。
- 完成后订单状态为 `COMPLETED`，`completed_at` 有值。

### 阶段 2：补齐收货地址管理

目标：C 端用户可以维护收货地址，下单时选择地址，并把地址写入订单快照。

后端改造：

- 新增 `mall_shipping_address` 表。
- 订单表增加收货地址快照字段，至少包含收货人、手机号、省市区、详细地址。
- 新增 C 端地址接口：列表、新增、编辑、删除、设置默认。
- 下单接口增加 `addressId`。
- 创建订单时校验地址属于当前买家和当前租户。

前端改造：

- 新增“地址管理”页面。
- 确认订单页支持选择默认地址和切换地址。
- 订单详情展示下单时的地址快照。

验证点：

- 用户只能维护自己的地址。
- 删除默认地址后的默认地址规则明确。
- 下单后修改地址不影响历史订单地址快照。

### 阶段 3：商品多层级类目管理

目标：后台维护类目树，商品关联类目，C 端支持按类目浏览。

后端改造：

- 新增 `mall_product_category` 表。
- 商品先采用单类目关联，给 `mall_product` 增加 `category_id`。
- 类目字段包含 `tenant_id`、`parent_id`、`name`、`sort`、`status`、`level`、`path`。
- 新增管理端类目接口：树查询、新增、编辑、启停、删除。
- 商品创建和更新支持 `categoryId`。
- C 端商品列表支持按 `categoryId` 筛选。

权限改造：

- 在用户中心商城权限目录增加：
  - `mall:category:create`
  - `mall:category:update`
  - `mall:category:delete`
  - `mall:category:list`
  - `mall:category:read`
- 将类目权限加入 `stacko-mall-admin` 门户策略。

前端改造：

- 管理端新增类目管理页面。
- 商品维护表单增加类目选择。
- C 端类目页展示类目树和商品列表。

验证点：

- 类目树不能形成循环。
- 删除类目前必须处理子类目和已关联商品。
- 不同租户类目数据隔离。

### 阶段 4：商品图片上传和展示

目标：后台可以维护商品主图、轮播图和详情图，C 端能展示真实商品图片。

后端改造：

- 新增 `mall_product_image` 表。
- 图片字段包含 `product_id`、`image_url`、`image_type`、`sort`。
- 初期支持保存图片 URL；上传存储先封装接口，后续接本地存储或对象存储。
- 商品响应返回主图、轮播图和详情图。

前端改造：

- 管理端商品表单增加图片维护。
- C 端商品列表展示主图。
- C 端商品详情展示轮播图和详情图。

验证点：

- 图片必须属于当前租户商品。
- 主图排序和缺省规则明确。
- 商品无图时前端有稳定占位展示。

### 阶段 5：商品收藏

目标：登录用户可以收藏商品，并在个人中心查看收藏列表。

后端改造：

- 新增 `mall_product_favorite` 表。
- 唯一键为 `tenant_id + buyer_id + product_id`。
- 新增 C 端接口：收藏、取消收藏、查询收藏状态、我的收藏列表。

前端改造：

- 商品详情页增加收藏按钮。
- 个人中心增加“我的收藏”入口和列表。

验证点：

- 匿名用户不能收藏。
- 重复收藏保持幂等。
- 下架或删除商品在收藏列表中的展示规则明确。

### 阶段 6：登录租户体验优化

目标：用户登录商城时不需要理解和手动输入租户 ID。

短期改造：

- C 端登录默认使用并隐藏 `stacko-mall` 租户。
- 管理端登录保留默认 `stacko-mall`，仅在高级场景允许修改。
- 登录成功后记忆当前租户。

长期改造：

- 用户中心支持按门户自动解析登录租户。
- 如果账号在当前门户只有一个可访问租户，登录请求允许不传 `tenantId`。
- 如果账号有多个可访问租户，用户中心返回候选租户，由前端选择后继续登录或切换。
- 复用用户中心已有 `/api/auth/tenants` 和 `/api/auth/switch-tenant` 语义，禁止前端单独伪造租户切换。

验证点：

- 单租户用户可无感登录。
- 多租户用户有明确选择入口。
- 门户不匹配时仍拒绝访问。

### 阶段 7：商品规格和 SKU

目标：从商品级库存升级到 SKU 级库存，支持规格选择、SKU 价格和 SKU 库存。

后端改造：

- 新增规格组、规格值、SKU、SKU 库存表。
- 无规格商品自动生成默认 SKU，兼容现有商品。
- 订单明细增加 `sku_id`、`sku_name`、`spec_snapshot`。
- 下单扣减 SKU 库存，不再直接扣商品库存。
- 商品响应返回规格矩阵和 SKU 列表。

前端改造：

- 管理端商品维护拆分基础信息、图片、规格、SKU 库存。
- C 端商品详情支持规格选择。
- 购物车和确认订单保存 SKU 信息。

验证点：

- SKU 唯一组合不重复。
- 库存扣减、支付、取消、关闭、退款释放库存逻辑正确。
- 老商品迁移后仍可购买。

### 阶段 8：迁移链和生产化补齐

目标：把业务演进形成可上线的数据库迁移和运维能力。

改造内容：

- 以当前重建脚本为基线补齐 Flyway 迁移链。
- 新增表、字段、索引全部进入 migration。
- 补齐订单、库存、支付、售后核心指标。
- 明确多实例订单超时任务的分布式锁或单实例策略。
- 完成核心链路压测和回滚方案。

验证点：

- 空库初始化和旧库升级都可验证。
- 数据迁移有回滚或补偿方案。
- 多实例下没有重复关闭订单或重复释放库存。

## 3. 阶段交付规则

每个阶段完成时必须给出：

- 改动文件清单。
- 数据库结构变更说明。
- 新增或变更接口说明。
- 前端入口和操作路径。
- 权限目录或门户策略变更说明。
- 已执行的测试或未能执行测试的原因。
- 下一阶段开始前的确认点。
